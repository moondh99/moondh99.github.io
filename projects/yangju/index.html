문제와 사용자본인 역할과 협업선택과 이유구현·진행 과정확인한 결과한계와 다음 확인

문제와 사용자

사용자 상황 버스의 현재 좌석 관측을 보고 이동을 판단하는 통근자와, 그 정보를 사용하는 화면·API.

좌석이 없는 경우와 정보를 받지 못한 경우를 같은 값으로 보여 주면 통근자가 상황을 잘못 판단할 수 있습니다.

본인 역할과 협업

좌석·도착 예정 시간에 필요한 데이터 항목과 API 응답 기준을 작성했습니다. 관측 시각과 최신성, 정보가 없는 경우의 표시를 정했습니다.

로컬 백엔드의 코드와 테스트는 AI와 협업했습니다. 본인은 원천 데이터와 HTTP 응답을 대조하고 구현 결과를 검토했습니다.

선택과 이유

좌석 0, 정보 미제공, 수집 실패를 나눠 응답 기준을 정했습니다. 관측 시각을 함께 전달하고, 근거가 없는 예측값은 null로 남겼습니다.

좌석이 0이면 관측된 값이고, -1·null이면 정보가 없을 수 있습니다. 이 차이를 화면에 전달하고, 오래된 정보도 알아볼 수 있도록 했습니다.

구현·진행 과정

  1. 조회 범위 확인

    4개 정류장·6개 노선/방향의 매핑을 원천 응답과 로컬 HTTP 기록으로 대조했습니다.

  2. 좌석과 결측 구분

    0은 관측 값으로 유지하고 -1·null·잘못된 값은 0으로 바꾸지 않습니다. 빈 차량 슬롯도 후보로 만들지 않습니다.

  3. 시각과 최신성

    좌석과 ETA에 수집 시각과 최신성을 붙입니다. 오래된 관측은 stale로 표시하는 응답 정책입니다.

  4. 읽기 전용 API

    이미 저장된 응답을 읽는 SQLite 어댑터와 current-seats API 구현을 확인했습니다. 예측 확률은 공개 근거가 없으면 null로 남깁니다.

확인한 결과

4개 / 6개정류장 / 노선·방향 매핑의 로컬 검증 범위

4개 정류장·6개 노선/방향의 매핑을 대조했습니다. 읽기 전용 API, 프론트 요청·응답 명세, DB 설계안과 검증 기록이 있습니다. 기존 기록의 수집 테스트 92개·API 테스트 183개 통과 및 PostgreSQL skip은 로컬 개발 검증 범위입니다.

한계와 다음 확인

팀 통합·예측 성능 평가·공개 서비스 배포는 아직 진행 전입니다. 현재 좌석 관측은 탑승 가능성을 보장하는 값이 아닙니다.
